# Documento de Requerimientos del Sistema de Gestión Social

Este documento contiene la especificación de **Requerimientos Funcionales (RF)** y **Requerimientos No Funcionales (RNF)** del **Sistema de Gestión Social (Servicio Social - Sistema de Gestión Universitaria)**, implementado en Python y Flet con base de datos SQLite.

---

## 1. Requerimientos Funcionales (RF)

A continuación, se detallan los requerimientos funcionales agrupados por módulos o áreas de funcionalidad dentro del sistema.

| Grupo de Requerimiento | Código | Requerimiento Funcional | Descripción |
| :--- | :--- | :--- | :--- |
| **Acceso al Sistema** | **RF01** | Iniciar Sesión | El sistema debe permitir a los usuarios autenticarse ingresando su nombre de usuario (`username`) y contraseña. El acceso estará restringido únicamente a cuentas marcadas como activas en la base de datos. |
| **Acceso al Sistema** | **RF02** | Cerrar Sesión | El usuario autenticado debe poder cerrar su sesión de manera segura, lo cual limpiará el estado del usuario en la aplicación y lo redireccionará a la pantalla de login. |
| **Acceso al Sistema** | **RF03** | Recuperar Contraseña | El usuario debe disponer de una opción para restablecer o recuperar su contraseña en caso de olvido (funcionalidad proyectada/administración de credenciales). |
| **Dashboard Analítico** | **RF04** | Filtrado de Métricas del Dashboard | El usuario debe poder filtrar la información analítica del Dashboard seleccionando un Mes específico (o la opción de "Todo el Año") y un Año. Las métricas y gráficos deben actualizarse automáticamente al cambiar estos filtros. |
| **Dashboard Analítico** | **RF05** | Visualización de Resumen de Atenciones | El sistema debe mostrar indicadores clave (cards) con el número total de atenciones registradas en el periodo y el desglose correspondiente a las categorías de casos sociales: *Evaluación*, *Evaluación y Seguimiento*, *Seguimiento* y *Orientación*. |
| **Dashboard Analítico** | **RF06** | Gráfico de Demografía por Género | El sistema debe presentar un gráfico circular (donas/anillos) indicando el porcentaje y la cantidad absoluta de atenciones realizadas a varones (M) y mujeres (F) en el periodo seleccionado. |
| **Dashboard Analítico** | **RF07** | Gráfico de Tipología de Usuario | El sistema debe mostrar un gráfico analítico de anillo indicando el porcentaje y número de atenciones correspondientes a Estudiantes activos y Egresados. |
| **Dashboard Analítico** | **RF08** | Ranking de Facultades con Mayor Atendidos | El sistema debe visualizar un listado de las facultades ordenadas por volumen de atenciones. Debe incluir un botón tipo acordeón ("Ver más / Ver menos") que permita alternar entre el Top 5 y la lista completa de facultades para optimizar el espacio en pantalla. |
| **Dashboard Analítico** | **RF09** | Gráfico de Evolución Mensual | El sistema debe graficar en barras la evolución histórica de las atenciones mes a mes (de enero a diciembre) para el año seleccionado, proporcionando etiquetas de cantidad y herramientas informativas (tooltips) al pasar el cursor. |
| **Dashboard Analítico** | **RF10** | Cambio de Tema Visual (Dark/Light) | El sistema debe permitir la alternancia en tiempo real entre el modo oscuro (Dark Mode) y el modo claro (Light Mode) a través de un botón en el encabezado, reajustando toda la paleta de colores de la interfaz. |
| **Registro de Atenciones** | **RF11** | Registrar Nueva Atención | El sistema debe permitir registrar una nueva atención en la bitácora de servicio social, recopilando: DNI, Fecha de Atención, Nombres, Apellidos, Edad, Sexo, Código Estudiante, Año de Estudio, Celular, Correo, Dirección, Observaciones, Tipo de Usuario, Caso Social, Facultad, Escuela Profesional y Modalidad de Ingreso. |
| **Registro de Atenciones** | **RF12** | Autocompletado Automático por DNI | Al ingresar un DNI de 8 dígitos en el formulario de registro, el sistema debe buscar si la persona ya cuenta con registros previos. De ser así, debe autocompletar automáticamente todos los campos personales y académicos del formulario para agilizar el proceso de atención. |
| **Registro de Atenciones** | **RF13** | Carga Dinámica de Escuelas Profesionales | En el formulario de registro y edición, al seleccionar una Facultad, el selector de Escuela Profesional debe desbloquearse y listar únicamente las escuelas asociadas a dicha facultad. |
| **Registro de Atenciones** | **RF14** | Campo Dinámico para Registro de Modalidad | Al seleccionar una modalidad de ingreso que requiera acreditación (ej. *Discapacidad* u otras modalidades especiales exceptuando *General* o *CEPREVAL*), el formulario debe mostrar dinámicamente un campo para capturar el N° de Registro o Carnet correspondiente (por ejemplo, el Código CONADIS). |
| **Registro de Atenciones** | **RF15** | Validación de Campos Obligatorios | El sistema debe validar que los datos obligatorios del formulario (DNI, Fecha, Nombres, Apellidos, Sexo, Tipo de Usuario, Caso Social, Facultad, Escuela y Modalidad) estén presentes y sean correctos antes de guardar el registro, mostrando mensajes de error inline. |
| **Registro de Atenciones** | **RF16** | Limpieza de Formulario de Registro | El formulario de registro de atención debe incluir una opción para restablecer todos los campos a su estado vacío o predeterminado (como la fecha de atención al día de hoy). |
| **Registro de Atenciones** | **RF17** | Flujo Integrado de Ficha Socioeconómica | Al guardar exitosamente una nueva atención bajo los Casos Sociales de *Evaluación* o *Evaluación y Seguimiento*, el sistema debe detectar esta condición y lanzar un diálogo modal preguntando al operador si desea rellenar la Ficha Socioeconómica del estudiante en ese momento. |
| **Gestión de Estudiantes** | **RF18** | Visualización Paginada de Estudiantes | El sistema debe mostrar el listado de personas registradas en una tabla interactiva con controles de paginación que permitan configurar la visualización a 10, 20, 50 o 100 registros por página. |
| **Gestión de Estudiantes** | **RF19** | Pestañas de Clasificación (Activos/Inactivos) | La vista de gestión debe separar los registros mediante pestañas: *Activos* (estudiantes con registro vigente) e *Inactivos* (registros archivados o dados de baja). |
| **Gestión de Estudiantes** | **RF20** | Filtros Avanzados y Multi-selección | El usuario debe poder realizar búsquedas textuales rápidas (por DNI, nombres, apellidos o código) y aplicar simultáneamente filtros multi-selección con checkboxes flotantes para Modalidad de Ingreso, Mes y Año de atención. |
| **Gestión de Estudiantes** | **RF21** | Ordenamiento Dinámico de Columnas | Al hacer clic en las cabeceras de columnas específicas en la tabla (Fecha, DNI, Apellidos, Modalidad, Tipo de Usuario, Facultad), la lista de estudiantes debe ordenarse de manera ascendente o descendente según corresponda. |
| **Gestión de Estudiantes** | **RF22** | Modificación de Datos de Estudiante | El operador debe poder editar la información completa de cualquier estudiante activo mediante un diálogo flotante organizado que cargue y valide los campos en tiempo real. |
| **Gestión de Estudiantes** | **RF23** | Desactivar / Reactivar Estudiantes | El sistema debe permitir cambiar el estado de un registro de Activo a Inactivo (desactivar) para archivarlo, o de Inactivo a Activo (activar) para restaurarlo en las listas principales. |
| **Gestión de Estudiantes** | **RF24** | Eliminación Definitiva de Registros | En la pestaña de Inactivos, el operador con permisos debe poder eliminar de forma permanente y definitiva el registro del estudiante de la base de datos. |
| **Gestión de Estudiantes** | **RF25** | Exportación de Listados a Excel | El sistema debe permitir exportar los registros de estudiantes filtrados en la tabla actual a un archivo Excel (`.xlsx`) estructurado y estilizado. El archivo se guardará en la carpeta de descargas del usuario con un nombre de archivo dinámico descriptivo según los filtros aplicados. |
| **Evaluaciones Socioeconómicas** | **RF26** | Dashboard de Impacto Socioeconómico | El módulo debe contar con un panel analítico que presente indicadores económicos clave: total de evaluaciones socioeconómicas completadas, promedio de ingresos familiares totales y promedio de gastos en alimentación. |
| **Evaluaciones Socioeconómicas** | **RF27** | Indicador de Clasificación SISFOH | El sistema debe mostrar la proporción de estudiantes clasificados según su vulnerabilidad en el SISFOH: *No Pobre*, *Pobre* y *Pobre Extremo*, mediante un gráfico circular de progreso. |
| **Evaluaciones Socioeconómicas** | **RF28** | Métrica de Acceso a Servicios Básicos | El sistema debe calcular y mostrar el porcentaje de estudiantes evaluados que disponen de agua por red pública, desagüe por red y energía eléctrica en sus viviendas mediante barras de progreso horizontales. |
| **Evaluaciones Socioeconómicas** | **RF29** | Listado de Estudiantes a Evaluar | Mostrar la lista de estudiantes activos que requieren una evaluación socioeconómica (registrados con casos de evaluación), detallando su DNI/Código, nombre, caso social, condición SISFOH, ingresos registrados y el estado de su ficha (*Completada* o *Pendiente*). |
| **Evaluaciones Socioeconómicas** | **RF30** | Rellenar y Editar Ficha Socioeconómica | El sistema debe proveer un formulario modal premium estructurado en 3 pestañas para la ficha socioeconómica: <br>1. **Salud y SISFOH:** Motivo de evaluación, condición SISFOH, tipo de seguro de salud y estado/nivel de discapacidad.<br>2. **Familia y Economía:** Estructura familiar, dinámica familiar, ingresos (familiares y de becas/bonos) y gastos mensuales (alquiler, alimentación, servicios, educación).<br>3. **Vivienda y Servicios:** Tipo de vivienda, material de construcción (paredes/techos) y switches de acceso a servicios públicos de agua, luz y desagüe. |
| **Evaluaciones Socioeconómicas** | **RF31** | Filtrado y Paginación de Evaluaciones | El usuario debe poder realizar búsquedas en el listado de evaluaciones por DNI, nombres o código de estudiante, filtrar por el estado de la ficha (Completada/Pendiente), mes y año de la atención, y navegar de forma paginada. |
| **Configuración y Catálogos** | **RF32** | CRUD de Catálogos Simples | Permitir a los administradores agregar, editar y cambiar el estado (Activo/Inactivo) de los registros de catálogos maestros: *Tipos de Usuario*, *Casos Sociales*, *Facultades* y *Modalidades de Ingreso*. |
| **Configuración y Catálogos** | **RF33** | Validación de Duplicidad en Catálogos | El sistema debe evitar la creación de registros duplicados en los catálogos simples, mostrando alertas en caso de que ya exista un elemento activo con el mismo nombre. |
| **Configuración y Catálogos** | **RF34** | CRUD de Catálogo de Escuelas Profesionales | Permitir gestionar el catálogo de Escuelas Profesionales, requiriendo asociar obligatoriamente cada escuela profesional a una Facultad activa registrada en el sistema. |
| **Configuración y Catálogos** | **RF35** | Configurar Parámetros de Respaldos | El sistema debe permitir definir la carpeta de destino donde se guardarán las copias de seguridad de la base de datos local SQLite. |
| **Configuración y Catálogos** | **RF36** | Programación de Copias de Seguridad Automáticas | Permitir activar/desactivar la ejecución de respaldos automáticos y definir su frecuencia o intervalo en días (Diario, Semanal, Quincenal, Mensual). |
| **Configuración y Catálogos** | **RF37** | Ejecución de Respaldo Manual | Permitir realizar de forma inmediata y manual un respaldo completo de la base de datos (`servicio_social.db`) en la ruta configurada, mostrando un mensaje informando el éxito de la operación o la descripción detallada del error en caso de fallo. |

## 2. Requerimientos No Funcionales (RNF)

Los requerimientos no funcionales definen los atributos de calidad, restricciones y especificaciones técnicas que debe cumplir el sistema para garantizar una experiencia segura, eficiente y robusta.

| Categoría | Código | Requerimiento No Funcional | Descripción |
| :--- | :--- | :--- | :--- |
| **Usabilidad (UX/UI)** | **RNF01** | Diseño de Interfaz Consistente | La interfaz gráfica debe mantener una estética profesional, limpia y moderna en todas sus vistas, implementando componentes unificados bajo la biblioteca de diseño de Flet. |
| **Usabilidad (UX/UI)** | **RNF02** | Contraste de Colores (Modo Claro/Oscuro) | El sistema debe garantizar que el contraste de color entre el fondo y el texto sea suficiente para una óptima lectura tanto en el modo claro como en el oscuro, cumpliendo con principios de accesibilidad visual. |
| **Usabilidad (UX/UI)** | **RNF03** | Soporte de Navegación Intuitiva | El sistema debe disponer de un menú lateral (`Sidebar`) persistente y de fácil comprensión que permita el cambio rápido entre módulos sin recargar la aplicación completa o perder datos temporales. |
| **Usabilidad (UX/UI)** | **RNF04** | Formateo Numérico Automático | Los campos de entrada numéricos monetarios de la Ficha Socioeconómica deben validar la entrada en tiempo real (solo dígitos y un punto decimal) y autocompletar el formato a dos decimales (ej. `0.00`) al perder el foco, facilitando el ingreso de datos económicos. |
| **Usabilidad (UX/UI)** | **RNF05** | Mensajes de Notificación Claros | Todas las operaciones críticas (guardar, actualizar, desactivar, activar y respaldar) deben mostrar notificaciones flotantes temporales (`Snackbars`) en la parte inferior de la pantalla para dar retroalimentación inmediata del estado de la acción al operador. |
| **Seguridad** | **RNF06** | Control de Acceso y Autenticación | La aplicación debe bloquear el acceso a todas sus pantallas principales hasta que el operador se haya autenticado de manera correcta en el módulo de login. |
| **Seguridad** | **RNF07** | Encriptación de Contraseñas de Usuario | Las contraseñas de los usuarios operadores y administradores deben almacenarse en la base de datos aplicando una función criptográfica hash segura (tipo bcrypt) para evitar filtración de credenciales. |
| **Seguridad** | **RNF08** | Confirmación de Operaciones Destructivas | Las acciones que impliquen la eliminación definitiva de datos (como el borrado de un estudiante) deben requerir la confirmación del usuario mediante diálogos de alerta modales flotantes antes de proceder. |
| **Seguridad** | **RNF09** | Integridad y Prevención de Inyección SQL | Toda interacción con la base de datos SQLite debe gestionarse a través del ORM SQLAlchemy utilizando consultas parametrizadas, neutralizando cualquier riesgo de inyección de código SQL malicioso. |
| **Rendimiento** | **RNF10** | Paginación Eficiente de Listados | Para mantener una interfaz fluida e impedir el consumo excesivo de memoria del equipo del cliente, las tablas de consulta de estudiantes y evaluaciones deben limitar el número de registros en pantalla a través de paginación controlada. |
| **Rendimiento** | **RNF11** | Procesamiento de Tareas E/S en Hilos | Operaciones de entrada/salida que puedan demorarse o bloquear el hilo principal (como el diálogo nativo de selección de carpetas del sistema operativo para respaldos) deben ejecutarse en hilos secundarios (`threading.Thread`) para evitar que la aplicación se congele. |
| **Rendimiento** | **RNF12** | Tiempos de Respuesta de Consultas | Las búsquedas, filtros avanzados y ordenaciones sobre la base de datos local no deben superar un tiempo de respuesta de 1.5 segundos en condiciones normales de hardware. |
| **Confiabilidad** | **RNF13** | Mecanismo de Tolerancia a Fallos de Red | El sistema debe funcionar de manera 100% local e independiente de una conexión de red o internet para la consulta e ingreso de información, almacenando los datos de forma segura en SQLite. |
| **Confiabilidad** | **RNF14** | Respaldo Automatizado | El sistema debe contar con un gestor automático de respaldos (`BackupManager`) que ejecute y valide una copia de seguridad física de la base de datos al cerrar/iniciar la aplicación según la periodicidad programada por el usuario. |
| **Mantenibilidad** | **RNF15** | Arquitectura de Software Modular (MVC) | El código del sistema debe estructurarse con separación limpia de responsabilidades: definición de base de datos y modelos (`database/`), lógica de control y consultas (`controllers/`) y presentación visual (`views/`), simplificando futuras ampliaciones del software. |
| **Compatibilidad** | **RNF16** | Portabilidad del Ejecutable / Aplicación | La aplicación desarrollada con Flet en Python debe poder ejecutarse de forma nativa e idéntica en entornos de escritorio de sistemas operativos Windows, macOS y Linux. |
| **Compatibilidad** | **RNF17** | Compatibilidad Universal del Formato de Reportes | Los archivos de reporte Excel exportados por la aplicación deben ser conformes a la especificación estándar OpenXML, garantizando su correcta apertura en Microsoft Excel, LibreOffice Calc, Google Sheets y WPS Office. |
